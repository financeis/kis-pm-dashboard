# 미해결 문제

## [시세]가 목표 시간보다 느림

- 증상: 대회 종목 527개·가격 이력 약 13만 행 상태에서 [시세]가 30~37초(통합문서를 연 뒤 첫 실행 약 44초). 사양 목표는 10~30초.
- 원인: 가격 이력 저장소 쿼리가 자기 표 13만 행을 읽어 마지막 봉만 바꾼 뒤 표 전체를 다시 쓰고, 가격 지표가 같은 표를 다시 읽는다(세 단계 합 약 17초 + 대회종목 표·테마 집계·토큰).
- 영향: 장중에 자주 누르는 버튼의 대기 시간. 데이터 정확성에는 영향 없음.
- 지금 못 고치는 이유: 저장소를 '확정 이력 + 당일 봉' 두 표로 나누거나 지표를 증분 계산하는 구조 변경이 필요하고, 버튼 순서·이관·검증 전체를 다시 확인해야 한다.
- 가능한 방법: 당일 봉만 담는 작은 표를 따로 두고 [전체]에서만 저장소에 합치기, 지표는 확정 이력 기준값을 캐시해 당일 봉으로만 갱신.

## 기존 [시장] 업종 히트맵에서 KOSDAQ 업종이 가끔 빠짐

- 증상: [모두 새로 고침] 때마다 KOSDAQ 제조·건설·통신·IT 서비스 업종이 무작위로 빠진다.
- 원인: 업종 구분별 전체시세 API(FHPUP02140000)가 KOSDAQ 목록을 100행에서 자르고 호출마다 내용이 달라진다.
- 영향: [시장] 히트맵의 KOSDAQ 칸만. [업종] 페이지는 업종 마스터 파일로 목록을 만들어 영향 없음.
- 지금 못 고치는 이유: 기존 화면이라 이번 범위 밖이었다.
- 가능한 방법: 히트맵도 업종 마스터 파일로 코드 목록을 만들고 업종별 시세를 따로 조회.

## 장 시작 직후 [시세]가 막히는 시간대 미측정

- 증상: 개장일 09:00 이후 KIS의 오늘 KOSPI 일봉이 생기기 전까지 [시세]는 저장소를 건드리지 않고 `오류: 오늘 세션 미확인` 1건을 낸다. 10:50에는 이미 생겨 있었지만 처음 생기는 시각은 모른다.
- 영향: 장 초반 [시세] 결과가 비어 보일 수 있다(어제 봉을 덮어쓰지 않으려는 의도된 동작).
- 지금 못 고치는 이유: 장 시작 시각에 직접 관찰해야 한다.
- 가능한 방법: 개장일 09:00~09:30에 1분 간격으로 KOSPI(0001) 일봉을 조회해 시각을 기록하고, 늦으면 멀티 시세 응답의 영업일자 등으로 오늘 세션을 확인하는 대안 검토.

## 특수 개장 시간 미반영

- 증상: 10시 개장일에는 09:00~10:00에 `오류: 오늘 세션 미확인`이 뜨고, 수능일처럼 마감이 늦은 날도 15:30을 완료 기준으로 쓴다.
- 지금 못 고치는 이유: KIS에 특수 개장 시간을 주는 API를 확인하지 않았고, 연 1~2회라 우선순위가 낮다.
- 가능한 방법: [설정]에 특수 개장일·시간 표를 두고 세션 규칙이 참조.

## 12~3월 주주총회 일정 일부 누락

- 증상: 12/31 기준일 정기주총은 수천 행이라 그 날짜를 건너뛰고 이벤트 표에 `오류: 주주총회 … 일부 누락 가능` 1건이 생겨 [전체] 상태가 `일부 오류`가 된다(대략 12~3월).
- 지금 못 고치는 이유: 시장 전체 목록을 다 받으면 [전체]가 크게 느려진다. 대회 기간(10~11월)에는 해당 없음.
- 가능한 방법: 그 기간에는 페이지 행 종목만 종목별로 조회(종목당 1회, 약 530회)하거나 보유·관심만 종목별 조회.

## 업종 페이지 수급 열 색이 대부분 노랑

- 증상: KRX 업종 수급 열은 전기·전자·제조 같은 큰 업종이 극단값이라 나머지 칸이 거의 노랑이다.
- 원인: 사양대로 열마다 최솟값·중앙값·최댓값을 기준점으로 쓴다.
- 지금 못 고치는 이유: 기준점 방식은 사용자가 정할 일이다.
- 가능한 방법: 업종 페이지만 5·50·95 백분위 기준점(대회종목 줄무늬와 같은 방식)으로 바꾸기.

## 평일 [전체]가 예상(2~4분)보다 김

- 증상: 평일 [전체]가 275~320초(4.6~5.3분)이고, 통합문서를 연 뒤 첫 실행은 준비·대기로 약 1.5~3분 더 걸린다.
- 원인: 평일에도 종목 수급 약 530회(종목당 1회), 목표주가 약 300회(값이 있던 종목), KIS 추정 약 110회, 이벤트 75회, KRX 업종 46회 등 약 1,100회 호출이 필요하고, Power Query의 순차 호출은 초당 약 5회다.
- 영향: 장 마감 뒤 하루 한 번 기다리는 시간. 데이터에는 영향 없음.
- 지금 못 고치는 이유: 호출 수를 줄이려면 갱신 주기(예: 목표주가·업종을 격일로) 같은 사용자 결정이 필요하다.
- 가능한 방법: KRX 업종은 [업종] 버튼에만 두기, 목표주가 매일 조사 대상을 최근 변경 종목으로 좁히기, 종목 수급을 보유·관심 + 대회 상위 종목으로 나누기.

## 공통 로직이 쿼리마다 따로 구현돼 있음

- 증상: KIS 호출(`fnKisGet`·`fnKisGetPage`), 실행 모드·`started` 읽기, 종목코드 정규화가 `T_FlowU`·`T_SectorKRX`·`T_Est`·`T_Target`·`T_EstSnap`·`T_Fin`·`T_CSL`·`T_Events`·`fnARun` 등에서 조금씩 다르게 다시 구현돼 있다.
- 영향: 규칙(예: 모드 판정·코드 정규화)을 바꿀 때 한 곳을 빠뜨리면 화면마다 동작이 달라진다. 실제 예: `fnPageRows`는 수정표 코드를 앞뒤 공백만 잘라 분류에 넘기고 수정표 규칙은 제어문자까지 지우므로, 제어문자가 낀 코드로 `추가`한 종목은 종목DB의 대회편입은 Y가 되지만 대회종목 페이지 행이 되지 않는다(직접 입력으로는 거의 생기지 않음).
- 지금 못 고치는 이유: 버튼 쿼리 전부를 바꾸는 리팩터라 각 쿼리의 재계산·요청 수 검증을 모두 다시 해야 한다.
- 가능한 방법: `fnKisGet`이 `fnKisGetPage(…, "")`를 부르게 합치고, 모드·`started`는 `fnPxRunCtl`, 코드 정규화는 공용 함수 하나로 모으기.

## 이력 CSV 보호가 행 수만 비교함

- 증상: [전체]의 이력 CSV 저장은 스냅샷 표 행 수가 기존 CSV보다 적을 때만 덮지 않는다. 표가 한 번 줄어든 뒤 다시 쌓여 기존 CSV 행 수를 넘으면, 기존 CSV에만 있던 (일자, 종목코드) 행이 덮어쓰기로 사라진다(날짜 붙은 파일에는 그때의 표 내용만 있음).
- 영향: 스냅샷 표가 줄어드는 비정상 상황이 먼저 있어야 생긴다. 그때 버튼 상태에 `일부 오류 1건`이 뜨므로, 그 경고를 넘긴 채 여러 날 [전체]를 계속 눌렀을 때만 옛 스냅샷이 CSV에서 빠진다(Fwd PER 변화 1W·1M은 재구성 값으로 대체될 수 있음).
- 지금 못 고치는 이유: 매크로의 저장 로직을 바꾸면 시험 통합문서 검증과 실제 통합문서 재생성을 다시 해야 해서 이번에는 기록만 했다.
- 가능한 방법: 덮어쓰기 전에 기존 CSV의 (일자, 종목코드)가 모두 표에 있는지 확인하고, 빠진 키가 있으면 지금처럼 기존 파일을 두고 날짜 붙은 파일로 저장.

## [전체] 준비 대기 중 Esc 뒤 바로 다시 누르면 중복 호출 가능

- 증상: 세션 첫 [전체]의 대기(15초 + 준비 시간) 중 Esc로 멈추면 준비한 표는 이미 '준비됨'으로 기록된다. 곧바로 [전체]를 다시 누르면 준비·대기 없이 시작하는데, 그때 Excel의 백그라운드 재평가가 아직 돌고 있으면 full 모드에서 KIS를 다시 부른다.
- 영향: 요청이 겹쳐 시간이 조금 늘 뿐 데이터는 맞다. 1~2분 기다렸다 다시 누르면 생기지 않는다.
- 지금 못 고치는 이유: 매크로 시작 순서를 바꾸면 요청 수 계수 시험을 다시 해야 해서 이번에는 기록만 했다.
- 가능한 방법: 대기 마감 시각을 모듈 변수에 남겨, 다음 실행이 남은 시간만큼 마저 기다리게 한다.
