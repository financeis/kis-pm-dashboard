# 0008. 중복 호출은 started 가드로 막고 사전 준비는 [전체]만

## 배경
Excel은 새로 고침 직후 쿼리를 백그라운드에서 한 번 더 평가한다. 측정해 보니 버튼 한 번에 KIS 요청이 두 배가 됐고([전체]면 수천 회 추가), 조회가 값 단계에 있으면 build 모드에서도 요청이 나갔다. 통합문서를 연 뒤 첫 활성 새로 고침은 쿼리 안의 가드로도 막을 수 없었다.

## 결정
버튼 쿼리는 조회를 함수 단계에 두고 활성 모드에서만 부르며, 버튼이 쓰는 `started`보다 자기 표의 최신 조회시각이 늦으면 다시 조회하지 않는다. 매크로는 `mode`·`started` 쓰기에 실패하면 실행을 멈춘다. 세션 첫 실행의 겹침은 [전체]만 막는다 — 이번 Excel 세션에서 아직 새로 고치지 않은 [전체]의 표를 build 모드로 한 번 먼저 새로 고치고, 준비한 쿼리들의 재평가가 끝나도록 '15초 + 준비에 걸린 시간'(최대 120초)을 기다린 다음(재평가는 VBA에서 보이지 않아 시간으로 기다림 — 고정 15초는 실행당 135회 중 81회 중복, 이 방식은 0회), 준비의 조회시각과 같은 초가 되지 않게 시계가 다음 초로 넘어가길 기다려 활성화한다. 준비가 없는 버튼은 기다리지 않고 바로 `started`를 쓴다.

## 대안
- 가드 없음: [전체] 호출이 두 배(약 1,100 → 2,200회, 첫 구축은 약 1만 2천 회)이고 build 모드에서도 호출.
- 모든 버튼에 사전 준비: [시세] 첫 실행이 54초 → 79초, [업종] 30초 → 40초로 느려지는데 막는 중복은 약 20·47회(2초 미만)뿐이라 손해.

## 결과
- 자동화·시험은 `started`를 미리 넣지 말고 매크로가 쓰게 한다. 하네스 시험에서 `started`가 비면 가드가 꺼져 재평가 중복이 생긴다.
- [시세]·[업종]의 세션 첫 실행은 요청이 약간 겹칠 수 있다.
- 세션 첫 [전체]는 준비·대기로 약 1.5~3분 더 걸린다. 대기 없이 막으려면 실행 제어 표에 '지금 새로 고치는 표' 키를 두고 각 버튼 쿼리가 자기 차례에만 호출하게 해야 하는데, 모든 버튼 쿼리·VBA·빌더를 바꾸는 계약 변경이라 하지 않았다.
- 조회가 모두 실패해 직전 표로 돌아간 경우는 조회시각이 그대로라 재평가가 한 번 더 시도한다.
